**T1 Phase-0 INVESTIGATION ONLY (29-Jun) — root cause + blast radius confirmed; NO fix/design/deploy.** Scope = `system_metrics.disk_used_pct` (-1.0 live / 0.0 daily max).

**1. THE METRIC.** `scripts/capture_metrics_baseline.py::_get_disk_used_pct()` computes disk via **psutil** (`psutil.disk_usage(str(_ROOT)).percent`), `except ImportError: return -1.0`. Written to **`analytics.db`** (NOT the main DB): `system_metrics` (live snapshot every 5 min, cron `capture_metrics_baseline.py` `*/5 09–15 Mon-Fri`) + aggregated into `system_metrics_daily` (cron `--summarize` 16:16). Run by cron (the trading service does NOT write these).

**2. ROOT CAUSE (confirmed, reproduced).** **psutil is NOT installed in the VM shared venv** (`/home/ubuntu/systems/venv` → `ModuleNotFoundError: No module named 'psutil'`). So `_get_disk_used_pct()` → -1.0 (reproduced live). Leading hypothesis CONFIRMED: the collector uses a non-stdlib method (psutil) that fails; shutil would work (the tower proves it). The **0.0 daily max** = `_stats()` filters `sorted(v for v in values if v >= 0)`; all samples are -1.0 → filtered out → empty → returns the `{max:0,...}` default → `disk_used_max_pct=0.0`.

**3. HISTORICAL.** Broken since INCEPTION. `system_metrics` = 582 rows 2026-06-19T09:30 → 29-Jun; `disk_used_pct` is **-1.0 in 100% of rows** (MIN=MAX=-1.0, single distinct value). Never once valid. `system_metrics_daily.disk_used_max_pct=0.0` for every date (22–29 Jun shown).

**4. CONSUMERS / BLAST RADIUS — it is a CLEANLINESS fix, NOT a real hole.** The ONLY reader of the broken value is `capture_metrics_baseline._check_drift` (its own disk-drift alert, line 278), and it is **silently dead**: it guards on `if hist_disk` where `hist_disk = MAX(disk_used_max_pct)` = 0.0 (falsy) → the disk branch never fires (and even if it did, `0 > 0*0.8` is False). NO other module reads `system_metrics.disk_used_pct` / `disk_used_max_pct` / `disk_used_avg_pct`. **Real disk-full monitoring is INTACT and independent:** `scripts/disk_monitor.py` (hourly cron) computes disk **fresh via `shutil.disk_usage(project_dir)`** with warning/critical thresholds + cleanup + Telegram — it never reads `system_metrics`. So **no disk-full condition goes undetected.**

**5. CONTROL TOWER — insulated.** `ops/control_tower/size_logger.py` computes `disk_used_pct` FRESH via `shutil.disk_usage()` (round(used/total*100,2)) and writes it to `control_tower_trends`; the tower's `disk.py`/`aggregator.py`/`reporter.py` read THAT value, never `system_metrics`. size_logger even carries the comment "computed FRESH … NOT the broken system_metrics.disk_used_pct". **Two-value relationship:** `system_metrics.disk_used_pct = -1.0` (broken, effectively unused) vs `control_tower_trends.disk_used_pct` = correct fresh value (the tower already has the right number).

**6. ROOT CAUSE + FIX ISOLATION.** Root cause = missing `psutil` in the VM venv (env/dependency) + the disk step's method choice (psutil instead of stdlib shutil). **Fix is ISOLATED:** `_get_disk_used_pct()` is a separate function from `_get_db_size_mb`/`_get_log_size_mb`, which use **pathlib** (not psutil) and are reliable (db 177 MB, log 690 MB live). Swapping the disk step to `shutil.disk_usage` (mirroring size_logger) would NOT touch the working pathlib metrics; the daily 0.0 self-heals once disk returns a >=0 value (the `_stats` filter then keeps it).

**LEAN FIX — BUILT + DEPLOYED 29-Jun (main `1e74bf6`; collector-cron ONLY; NO trading-code/parity change, NO schema, NO restart; branch deleted → main single source).** ONE function changed: `scripts/capture_metrics_baseline.py::_get_disk_used_pct()` now `shutil.disk_usage(_ROOT)` → `round(used/total*100, 2)` (mirrors size_logger/disk_monitor); psutil NOT installed (scope-locked — left absent). cpu/mem/fds keep their psutil −1.0 fallbacks (untouched); db/log sizes (pathlib) unchanged. **Disk-drift branch GATED OFF** in `_check_drift` (`if False and hist_disk …` + comment) — the repair makes `hist_disk` truthy, which would otherwise REVIVE the redundant disk alert; disk alerting is owned by `disk_monitor.py`. Historical −1.0 rows left as-is (no backfill). 27 tests `tests/unit/test_capture_metrics_baseline.py` (disk valid %; db/log unchanged; disk-drift inert even with a 95%-vs-40% spike) green. **VM LIVE-VERIFIED:** deployed `1e74bf6` has `shutil.disk_usage(_ROOT)` (L127) + `if False and hist_disk` (L287); psutil `ModuleNotFoundError` (absent); `_get_disk_used_pct()` = **12.74%** == `shutil used/total` == `df` 13% (rounding/reserved-block); a real collector snapshot landed a VALID 12.74 row in `analytics.db` (prior 15:55 row still −1.0); `--summarize --dry-run` self-heal = valid disk max 12.74 (db/log unchanged; cpu/mem still 0). **Today's OFFICIAL `system_metrics_daily` row stays 0.0** (today's market-hours samples were pre-fix); **tomorrow's 16:16 `--summarize` is the first fully-valid daily row** (no backfill). Lands live on the next */5 collector run during market hours (no restart).

**COLLATERAL (out of T1 scope — disk only — but flag for sizing):** the SAME missing-psutil root cause also breaks `cpu_pct` + `memory_mb` (both -1.0 → daily 0.0) and `open_fds` (-1) in `system_metrics`, and silently disables the cpu/memory drift alerts (hist=0.0 falsy). `thread_count` survives (threading fallback). DEEPER design note: this cron measures its OWN short-lived process (not the trading service), so cpu/mem/fds/threads aren't meaningful even with psutil — but **disk is system-wide, so disk is the one genuinely useful metric here**, and it's broken purely by the missing dep. Fix options to weigh later: (a) minimal — swap disk step to shutil (isolated, disk-only); (b) broader — `pip install psutil` in the VM venv (restores disk+cpu+mem+fds at once, but cpu/mem still measure the wrong process).
