**Method:** ran all 3 generators (new `reports/daily_trade_review.py`, old DB-pure `daily_review.py`, old non-DB `daily_report.py`) against 6 dates (16/17/22/24/29/30-Jun) on real VM backup DBs, via 6 parallel Opus subagents (one per date), each independently extracting shared facts (trade count, gross/net P&L, charges, win/loss, per-strategy nets, slippage, capital open/close) and classifying every divergence as IMPROVEMENT/EXPECTED/NEW-BUG.

**Gotcha discovered mid-setup:** VM daily backups dated D reflect state through end of day D-1 (nightly 01:00 IST cron) — to see date D's own trades you need the D+1-dated backup (or later). 16/17-Jun have no dedicated backup (14-day retention) — used the earliest available (22-Jun-dated, containing data through 21-Jun) as source, confirmed row-identical to today's live DB for those dates (immutable historical rows, not pruned).

**★ NEW-BUG #1 (confirmed, fix before Phase C): win%-denominator dilution.** Strategies sheet (T1 per-strategy, T3 per-direction) and the Dashboard's "direction skew" highlight compute `win% = wins / ALL trade-attempt records` (including never-filled FAILED/REJECTED rows), while wins can only come from filled trades — producing a diluted, misleading win% that contradicts the Dashboard's own correct headline (e.g. 30-Jun: headline 50% vs T3-LONG 29.41% for the identical population). **Confirmed independently on 3/6 dates (22-Jun, 29-Jun, 30-Jun)** by 3 separate subagents that weren't told to look for it on the first 2 — genuine cross-date convergence, universal not date-dependent. Doesn't touch any monetary figure; fix = swap denominator to filled/completed-trade count (matching the Dashboard headline convention already used correctly elsewhere in the same sheet).

**NEW-BUG #2 (cosmetic, low severity):** Dashboard's "Signals coverage" note hardcodes a static "82% webhook-dropped" figure (line ~2055) instead of computing per-date — wrong on 16-Jun (actual 42%). Sits in a descriptive note only, no load-bearing number affected.
