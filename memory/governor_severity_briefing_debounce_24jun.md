**Two independent alerting-correctness fixes, one branch `governor-severity-and-briefing-debounce-24jun`. No schema, no trade-path; both activate next restart / next cron run.**

## FIX 1 — strategy_governor lost circuit-breaker alert (missing `severity`)
`capital/strategy_governor.py:149` (`_pause_strategy`) called `self._notifier.send(title=, body=, source_module=)` with **no `severity`** — a REQUIRED keyword-only arg on `TelegramNotifier.send` — so every strategy-circuit-breaker trip raised `TypeError: ...missing 1 required positional argument: 'severity'`, which the surrounding `try/except` swallowed (`strategy_governor.notifier_failed`) → **the "STRATEGY PAUSED" alert was silently lost**. Surfaced as today's only 2 TypeErrors (Issue-3 side-finding). **It was the ONLY caller missing severity** (grepped every `.send(` site; all others pass it). **Fix:** added `severity="WARNING"`. Severity rationale = convention: `kill_switch` HALTs are CRITICAL; a single-strategy daily-loss pause is a protective action working as designed (other strategies keep trading) = WARNING (matches `breakeven_manager`/`main.py` config events). **Why it never surfaced earlier:** the governor trip path (today_pnl < loss_multiplier × avg_daily_loss, pre-cutoff) was rarely/never hit live until now; the existing test used a bare `MagicMock` notifier that accepts any args → hid the missing-arg bug. **Tests:** added `_StrictNotifier` (enforces the real keyword-only signature; the bug → `calls` empty) + `test_pause_alert_dispatches_with_required_severity` (regression — fails on old code) + severity assertion on the existing MagicMock test.

## FIX 2 — 09:20 briefing false-CRITICAL (heartbeat-commit race) → grace debounce
The Cron Officer morning briefing computes severity over jobs; `_compute_severity` returns CRITICAL on any FAILED/MISSED. The briefing uses `now_time = officer.morning_briefing_time` (a **FIXED** 09:20, not wall-clock). `_classify_job` marked a heartbeat_db job MISSED the instant `now_time >= due_time` with no heartbeat row — so a job firing right at 09:20 (e.g. the */5 `capture_metrics`, or any sibling in the 09:20 cron cluster) whose heartbeat hadn't committed when the briefing snapshotted → **transient MISSED → daily false CRITICAL** (recompute seconds later = INFO). Issue-1 had already made this HARMLESS (clean email); this removes the false CRITICAL itself.

**Chose Option B (debounce/grace) over Option A (stagger to 09:2X):** the standing rule is fix-the-root-cause, and the root cause is "a just-fired job's heartbeat-commit lag is read as a miss." A grace window fixes that directly, is **timing-agnostic** (I couldn't pin the exact racer from logs — the diagnosis was inferential — so "commits late unpredictably" applies), **preserves real-miss detection fully** (stagger would too, but grace needs no schedule change), and **avoids the self-maintaining-crontab churn** (no `cron_expression` change → generated crontab byte-identical → 4-way sha intact; verified). **Impl:** `OfficerConfig.miss_grace_minutes` (default **2**, also in the yaml officer block); `_classify_job` gained a `grace_minutes` param — a heartbeat_db job with no row that is due but within `grace` minutes of `now_time` → **PENDING** (just fired), not MISSED; `build_report` passes `registry.officer.miss_grace_minutes`. A genuinely missed job (due > grace ago) → still MISSED → still CRITICAL (proven: `test_within_grace_does_not_escalate_but_real_miss_does`). Applies to the EOD report too (harmless — EOD already fires +5 min after the last job). **Tests:** +6 in `test_cron_officer.py` (within-grace→PENDING; grace=0→MISSED i.e. old behaviour; past-grace→MISSED; committed→COMPLETED; escalation INFO-vs-CRITICAL; default=2).

**Live proof:** next governor trip → alert dispatches with severity (no TypeError). Tomorrow's 09:20 briefing → INFO (not false CRITICAL) absent a real miss; if still CRITICAL → a genuine miss, investigate that job.
