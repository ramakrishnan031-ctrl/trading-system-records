19-Jun-2026 cleanup of stale CRITICAL sentinel flags on the **PC** (dev machine).

**Finding:** PC `data_store/` held **445** `critical_alert_*.flag` files spanning **31-May → 18-Jun** (96 from 20260531, then ~30-78/day through 18-Jun). A sampled flag was a **test artifact**: `{"title":"Test","body":"Body","source_module":"test","hostname":"DESKTOP-029USHU"}` — i.e. generated by running the system/tests on the PC, never consumed (no `.delivered`/`.failed` on PC, because `alert-watcher.service` runs on the **VM only**).

**Git status:** all of `data_store/` is gitignored (`.gitignore` line 14 `data_store/`), so these flags were **never tracked** (`git ls-files data_store/ | grep critical_alert` = 0). `.gitkeep` is the only force-tracked file there. **No `.gitignore` change or commit was needed** — the dir-level ignore already covers `critical_alert_*.flag`.

**VM was already clean:** 0 `.flag`, 0 `.failed`, 21 `.delivered` (17 from 18-Jun, 4 from 19-Jun) — alert-watcher consumes flags → `.delivered` as designed; the VM's old 56 were removed 18-Jun (see [[task_4_system_map]]).

**Action:** deleted all 445 PC `critical_alert_*.flag` (`rm -f data_store/critical_alert_*.flag`). PC `data_store/` now holds only `trading_system.db`, `analytics.db`, `session/`, `.gitkeep` (local dev DBs — left intact). No VM change.

**Why:** stale, undelivered, mostly-test sentinels piling up on the dev box; harmless but noisy. **How to apply:** sentinel `.flag` files are local-only operational state (gitignored); the consumer is the VM alert-watcher. The PC accumulates them whenever the system/tests run locally with no watcher — periodically `rm data_store/critical_alert_*.flag` on the PC; never commit them.
